# Boyi Logistics OS Lite 架构方案

前期方案为了追求平台化，容易引入过多概念，例如 Module Runtime、Capability、Contribution、Dependency Resolver、Generation Manager 等，最终可能变成“造平台的平台”，影响实际业务效率。

本项目的目标不是开发通用 PaaS，而是：

> 把当前 `boyi-logistics` 渐进升级为轻量化、可扩展、AI 辅助的物流操作系统。

核心要求：

1. 现有后台模块保留，不改变使用习惯。
2. 自动化脚本保持高稳定、高效率，不经过 AI 决策。
3. 飞书固定命令直接进入确定性执行链路。
4. 只有不确定的问题才调用 AI Assistant。
5. 模块可以在后台受控安装、停用和升级。
6. 功能插件可以独立替换。
7. 模块之间数据互通。
8. 不引入厚重中间层。
9. 运行效率优先。

## 一、总体架构

```text
                         用户

        ┌─────────────────────────────┐
        │                             │
        ▼                             ▼

  Console 后台                   飞书机器人
  （主要入口）                   （远程入口）

        └──────────────┬──────────────┘
                       ▼

              交互路由与控制平面

        ┌──────────────┴──────────────┐
        ▼                             ▼

 固定业务路由                    AI Assistant
 （确定性任务）                  （非确定任务）

        │                             │
        ▼                             ▼

 自动化项目/插件                受限 Tool 调用

        └──────────────┬──────────────┘
                       ▼

                    业务模块层

 ┌──────────┬──────────┬──────────┬──────────┐
 运单       跟踪       客服       财务
 OCR        回单       调度       自动化
 └──────────┴──────────┴──────────┴──────────┘

                       ▼

                    统一数据层

 运单 / 客户 / 网点 / 财务 / 轨迹 / 问题件
```

当前实现中的 Command、Run、Approval、Evidence、Outbox、插件 generation 和 lease 是生产安全控制，不属于应删除的厚重中间层。

## 二、核心设计思想

### 不做

- 每个模块拆成独立系统
- 微服务拆分
- Kafka 或新的消息系统
- Kubernetes
- 第二套插件框架
- 第二套控制平面
- 全部业务 AI 化
- 为追求抽象而新增通用 Runtime

### 做

- 单体应用 + 模块化
- 在现有签名插件平台上扩展
- 统一数据库
- 统一权限入口
- 统一任务管理
- AI 作为辅助入口
- 真实来源优先、失败显式可见

## 三、保留现有后台结构

现有侧边栏继续保持业务认知边界：

```text
运单录入
寄件运单查询
物流跟踪
回单管理
客户服务
财务模块
货拉拉调度
专线分流
自动化
业务账号
```

这些是一级业务模块，不因技术重构而拆散或改名。新增模块注册能力时，应让现有导航逐步从单一注册源派生，不能重写 Console 或改变日常操作路径。

## 四、模块设计

业务模块应保持清晰的服务、接口、数据模型、页面和插件边界。概念结构如下：

```text
finance/
├── module.py
├── service.py
├── api.py
├── models.py
├── pages/
└── plugins/
```

该结构只是职责示意，不授权移动现有文件。当前财务权威实现已经分布在 `shared/finance/`、Agent 财务采集/同步和 Console 财务工作台中，后续 TASK 应优先注册现有能力，不能为了匹配示意目录而迁移代码。

财务模块概念组成：

```text
财务模块
├── 财务账本
├── 财务查询
├── 财务页面
└── 数据源/同步/BI 扩展
```

## 五、模块管理方式

未来增加轻量 Module Manager，负责：

- 安装模块
- 启用模块
- 停用模块
- 升级模块
- 展示模块状态
- 查看模块贡献的菜单、页面和权限

后台概念界面：

```text
系统管理
└── 模块管理
    └── 财务模块
        状态：已启用
        [停用] [升级] [查看插件]
```

Module Manager 只能管理业务模块注册，不得复制现有自动化插件安装、签名、代际切换和生命周期能力。

## 六、插件设计

插件是一个受控能力扩展，不建设开放式生态。

示例：

```text
automation_scan
功能：扫描同步
入口：系统定时 / 飞书 / 后台按钮
```

```text
finance_ronghui
功能：获取融辉财务数据
输入：业务日期
输出：经过校验的财务流水与汇总
```

概念生命周期包括安装、启用、停用和执行。当前仓库已经通过签名 manifest、项目实例、generation、lease 和 Broker 提供更严格的实现，因此禁止再新建一个简单 `Plugin` 基类作为平行运行时。

## 七、自动化中心设计

自动化中心管理：

```text
自动化任务
├── 扫描
├── 到货统计
├── 分批问题件
├── 自提问题件
├── 每日寄件同步
└── 财务同步
```

每个任务由现有自动化插件动作与独立项目实例承载。动作包不携带账号、资源、实际定时或审批策略；这些属于项目实例配置。

## 八、自动化触发机制

每个自动化按签名合同选择支持的入口，不能假设所有任务都支持全部入口。

### 系统定时

管理员在后台配置启用状态和实际执行时间。定时属于系统项目配置，不写入插件包。

### 飞书固定命令

```text
飞书事件
↓
固定命令路由
↓
唯一 committed 项目实例
↓
Command / Run
↓
签名插件动作
↓
受控结果回复
```

固定命令不经过 LLM。不得绕过 Command/Run 直接调用脚本。

### 后台按钮

后台“立即执行”从已保存项目配置派生参数，不允许浏览器提交工具名、账号或任意业务参数覆盖。

## 九、飞书机器人设计

飞书机器人保持两层路由。

### 第一层：固定命令

例如：

```text
扫描
统计
分批
自提到货问题件
查单 <运单号>
```

固定命令优先匹配，进入确定性项目实例。

### 第二层：AI Assistant

无法匹配固定命令且问题属于开放的只读查询范围时，才进入 AI Assistant，例如：

```text
最近哪个客户利润下降？
为什么本周异常件增加？
分析今天的经营情况。
```

AI 不得获得未开放的外部写能力，也不得绕过审批或项目绑定。

## 十、AI Assistant 设计

保持轻量：

1. 理解问题。
2. 选择已开放的只读或计算工具。
3. 调用业务查询服务。
4. 汇总真实结果。

```text
用户
↓
LLM
↓
受管 Tool Router
↓
业务查询服务
↓
真实数据结果
```

示例回复中的营业额、订单、利润和变化比例必须由真实查询即时计算；无数据或查询失败时明确返回“无数据”或失败原因，禁止填入演示数字。

## 十一、模块之间数据共享

采用三层共享方式，不引入新消息队列。

### 核心业务表

运单、财务、轨迹和问题件使用明确稳定的业务身份关联。现有表和仓储应优先复用，禁止为模块注册复制事实表。

### 查询服务

模块通过稳定查询服务共享数据，例如客服调用跟踪查询服务，而不是跨模块复制 SQL 或业务规则。

### 简单事件

重要状态变化使用现有 `domain_events` 和事务 Outbox，例如：

```text
waybill.created
tracking.exception
finance.sync.completed
```

新事件必须有明确生产者、消费者、Schema、幂等键和失败处理；不能把 Outbox 扩张为通用消息平台。

## 十二、财务模块设计

保持：

```text
财务模块
├── 财务流水
├── 费用映射
├── 账本
├── 融辉数据源
├── 待验收数据源
├── 同步任务
└── BI
```

数据流：

```text
已启用财务来源
↓
标准数据格式与 Decimal 校验
↓
共享财务核心
↓
MySQL
↓
Console BI
```

当前只允许共享来源注册表中已完成真实页面验收的来源进入生产。未验收来源不得调度、展示或回退到历史 Excel/CSV。

## 十三、BI 设计

保持轻量 BI，展示：

- 收入趋势
- 成本趋势
- 毛利趋势
- 客户排行

图表只消费服务端校验后的数据。浏览器不得重新计算财务金额；无成功数据的日期不得补零。

## 十四、数据库设计

保持一个 MySQL 数据库，不拆库。当前表已经按领域自然分组，包括：

```text
waybill / tracking / receipt / customer
finance_*
automation_*
agent_* / work_items / approval_* / evidence_*
domain_events / outbox_events
```

数据库结构只允许通过 `agent/migrations/` 的顺序 SQL 修改。任何 DDL 都必须单独授权、备份、预检和回滚，运行时服务不得自动建表或改表。

## 十五、插件安装升级流程

概念流程：

```text
上传签名插件包
↓
校验签名、版本和合同
↓
安装不可变版本
↓
准备目标 generation
↓
验证账号、资源、定时和运行条件
↓
原子切换 committed generation
```

失败时旧 generation 保持服务；未知写结果必须阻断，不得把“重启后再试”当作回滚。

## 十六、插件卸载

```text
停用项目实例
↓
停止新入口和新租约
↓
等待现有 lease 排空
↓
检查未知写和引用
↓
卸载实例
↓
最后引用消失后清理包字节
↓
保留业务数据和审计
```

卸载单个数据源或自动化实例不能影响其他实例及历史数据。

## 十七、部署方式

保持当前双服务与共享代码结构：

```text
/home/boyce/agent
├── agent
├── console
├── shared
└── first_party_automation_plugins
```

不拆服务。生产发布继续使用项目唯一发布脚本、共享 Python 环境、迁移前检、release hold、健康检查和精确回滚材料。

## 十八、运行效率保证

确定性自动化不经过 AI：

```text
固定入口
↓
受控项目实例
↓
确定性插件动作
```

查询优先直接调用业务 API 与数据库服务；只有复杂、不确定且已开放的只读分析进入 AI。不得给确定性链路设定未经实际采样的性能数字或 AI 占比目标。

## 十九、最终用户体验

飞书固定命令快速返回真实执行结果：

```text
扫描
→ 返回本次真实扫描结果或明确失败原因

统计
→ 返回本次真实到货统计结果或明确失败原因

今天营业额多少？
→ 查询共享财务账本后返回实际金额；无数据时明确说明
```

后台可以受控安装插件、配置项目实例、选择账号和资源、设置入口与定时，并查看运行、审批、证据和失败原因。
