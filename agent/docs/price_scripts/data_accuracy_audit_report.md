## 三、各节点错误数据过滤对照

batch_run.py 产生 4 种错误标记（存入"匹配网点名称"列，总费用=None，重量区间=""）：

| 错误标记 | 生成价格表.py | 生成明细单价表.py | 生成物流频次报价表.py | 过滤机制 |
|---------|-------------|-----------------|--------------------|---------|
| 地址解析失败 | ✓ `contains('失败')` | ✓ `contains('失败')` | ✓ `contains('失败')` | 显式 |
| 网点盲区 | ✓ 总费用=None→空值过滤 | ✓ 总费用=None→空值过滤 | ✓ `contains('网点盲区')` | 隐式/显式 |
| 目的地不可用 | ✓ 总费用=None→空值过滤 | ✓ 总费用=None→空值过滤 | ✓ 总费用=None→空值过滤 | 隐式 |
| 处理异常 | ✓ 总费用=None→空值过滤 | ✓ 总费用=None→空值过滤 | ✓ `contains('处理异常')` | 隐式/显式 |
| 服务大厅(正常网点) | **未过滤** | ✓ `contains('服务大厅')` | 主源已过滤/回退源保留 | **缺口** |

**结论：错误数据不会泄漏到定价输出（客户报价表/省城报价表），因为它们依赖的生成明细单价表.py 做了完整过滤。但生成价格表.py 的分析输出中包含"服务大厅"数据。**

## 四、发现的数据准确性问题

### 问题 1：生成价格表.py 未过滤"服务大厅"【中等】

**位置**：`生成价格表.py` 第 97 行

```python
fail_mask = df_raw['匹配网点名称'].str.contains('失败', na=False)
# ← 缺少: 服务大厅过滤
```

**影响**：
- 生成价格表.py 输出的分析 Excel（省级汇总、区县汇总、热力图等）包含"服务大厅"匹配的数据
- "服务大厅"通常指不可达的区域，其报价可能偏高或不准确
- **不影响客户报价表**（客户报价表读取的是生成明细单价表的输出，已过滤）

**修复建议**：在 `fail_mask` 后增加服务大厅过滤：
```python
hall_mask = df_raw['匹配网点名称'].str.contains('服务大厅', na=False)
df = df_raw[~fail_mask & ~hall_mask].copy()
```

---

### 问题 2：生成价格表.py 失败清单不完整【低】

**位置**：`生成价格表.py` 第 97-100 行

**现状**：`df_failed` 只包含"地址解析失败"的行（匹配网点名称含"失败"）。"网点盲区"、"处理异常"、"目的地不可用"这三类错误虽然被 `null_mask` 正确过滤掉了，但它们没有出现在"地址解析失败清单" Sheet 中。

**影响**：分析 Excel 的失败清单 Sheet 不完整，用户无法看到所有有问题的区县。

**修复建议**：扩大失败标记范围：
```python
fail_mask = df_raw['匹配网点名称'].str.contains('失败|网点盲区|处理异常|目的地不可用', na=False)
```

---

### 问题 3：生成物流频次报价表.py 回退源单价未用 Decimal【低】

**位置**：`生成物流频次报价表.py` 第 258 行

```python
df_raw['单价'] = df_raw['总费用'] / df_raw['最高单价对应重量(kg)']
```

**对比**：主数据源（生成明细单价表.py）使用 `Decimal(str(val)).quantize(Decimal('0.01'), ROUND_CEILING)`，而回退源使用 float 除法 + `round(val, 2)`。

**影响**：回退源的单价可能与主数据源有 ±0.01 元/kg 的微小差异。但回退源仅用于主数据源无覆盖的少量区域（服务大厅区域），实际影响很小。

---

### 问题 4：WEIGHT_MAP 回退值与实际测试重量差距大【低·几乎不触发】

**位置**：`生成明细单价表.py` 第 18-27 行，`生成价格表.py` 第 36-45 行

| 重量区间 | WEIGHT_MAP 回退值 | 实际数据中的典型值 | 偏差 |
|----------|-----------------|------------------|------|
| 101-150kg | 120 | 101.0 | +19% |
| 151-300kg | 200 | 151.0 | +32% |
| 301-350kg | 320 | 301.0 | +6% |
| 351-800kg | 500 | 351.0 | +42% |
| 801-1500kg | 1000 | 801.0 | +25% |
| 1501-3000kg | 2000 | 1501.0 | +33% |
| 3001+kg | 3500 | 3001.0 | +17% |

**影响**：WEIGHT_MAP 仅在"最高单价对应重量(kg)"列为空时作为回退使用。由于 batch_run.py 始终记录实际测试重量，正常数据 99%+ 有实际重量值，回退几乎不触发。但如果触发，单价会被低估（除数偏大）。

**现状验证**：生成明细单价表.py 第 96 行已打印使用实际重量的行数，可确认回退频率。

---

### 问题 5：config.json 包含硬编码凭证【安全·非数据准确性】

**位置**：`config.json` 第 2-5 行

```json
"test_user_data": {
    "operator_uid": "...",
    "operator_password": "..."
}
```

**现状**：login_manager.py 读取 config.json 中的凭证。同时 get_price.py 也通过 `.env` 读取。两处来源并存。

## 五、已确认的安全设计

以下是审计中确认**不存在问题**的关键环节：

### 1. 单价计算精度（已正确）

**链路**：batch_run.py 存储 `(总费用, 对应重量)` → 生成明细单价表.py 用 `Decimal(str(fee/weight)).quantize('0.01', CEILING)` 计算单价

- batch_run.py 第 179 行的 `fee / w` 是 float 除法，但**仅用于比较**哪个重量点的单价更高，不存储单价本身
- 实际存入 Excel 的是 `总费用`（原始 float）和 `最高单价对应重量`（原始 float）
- 下游脚本用 Decimal 重新计算单价，精度由下游控制，不受上游 float 比较影响

### 2. 错误数据不会泄漏到客户报价表（已正确）

- 生成明细单价表.py 是所有客户面输出的唯一数据源
- 该脚本依次过滤：失败 → 服务大厅 → 空值 → 0-100kg
- 所有 4 种错误标记的行总费用均为 None，一定会被空值过滤捕获
- 客户报价表、省城报价表、热力图只读取已过滤的明细单价表

### 3. 重量区间边界处理（已正确）

- `_available_products(800)` 返回 `[003, 004]`（≤800kg 的产品）
- `_available_products(801)` 返回 `[002, 003, 004]`（800<w≤3000 的产品）
- 与 CLAUDE.md 文档中的产品规则一致，与 weight_scan_analysis.md 的逐公斤扫描验证结果一致

### 4. 同名区县过滤（已修复）

- `_filter_best_destination()` 采用城市名→省份→回退的瀑布策略
- 已在 get_price.py、batch_run.py、weight_scan.py 三处统一修复
- repair_mismatch.py 将重跑受影响的 133 个区县

### 5. 断点续传一致性（已正确）

- `done_indices` 和 `results` 同步保存/加载
- 由于 `done_indices` 是 set，重复处理不可能发生
- 保存间隔 10 条，最多丢失最近 10 条的进度（需重跑）

### 6. 利润加计精度（已正确）

- `add_profit(val)` = `ceil2(val + 0.15)`
- 其中 `ceil2` 使用 `Decimal(str(val)).quantize('0.01', CEILING)`
- 加法在 float 域执行（0.15 可精确表示为 float），然后 Decimal 精确进位
- 最大误差：由于上游单价已 CEILING 进位，加 0.15 后再 CEILING 可能多 0.01
- 实际影响：每公斤最多多 0.01 元，在物流定价场景可忽略
